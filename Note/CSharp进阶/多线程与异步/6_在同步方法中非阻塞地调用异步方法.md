
## 1. 问题背景？
*某些情况下没办法将同步方法改写为异步*

1. 希望在类的构造方法中调用异步
2. 接口规定的是同步方法，必须实现，又必须在其中使用异步
3. 修改老项目时，不想因为异步的传染性，导致每一个方法都改动，需要在某个地方将异步隔离
4. UI启动时需要加载数据，但又不想卡UI

---

## 2. 总结先行

### 1.`Wait()` / `Result` / `GetAwaiter().GetResult()`
	- 能用，但本质是同步，会阻塞线程
### 2. Fire and Forget（一发即忘）
	- 不阻塞，但可能导致无法捕获异常，或程序崩溃
### 3. 使用回调思想包装一发即忘：
	- 能在异步侧线程处理异常(本质为 async void, 外层线程仍无法捕获异常)
### 4. 使用 `ContinueWith` 包装一发即忘：
	- 本质为 async Task, 可以解决异常被吞，但注意设置 TaskScheduler 避免死锁
### 5. 使用异步工厂替代类的构造函数：
	- 解决需要在类的构造函数中使用异步的问题
### 6.`IAsyncRelayCommand` / `TaskNotifier`：
	- 解决 WPF 中将异步绑定到事件或命令的问题

**总而言之，在同步里调异步并不简单，最佳实践应是：能使用异步就异步到底**

---

## 3. 方案一：阻塞等待

对应示例：[1_Blocking/Program.cs](../../../Code/CSharp进阶/多线程与异步/6_在同步方法中非阻塞地调用异步方法/1_Blocking/Program.cs)

两类写法：

```csharp
//1. 使用 .Wait()或.Result() 方法以"阻塞"形式等待异步方法完成（这可能会造成死锁!）
FooAsync().Result;
FooAsync().Wait();

//2. 使用 .GetAwaiter().GetResult() 方法，依旧阻塞，依旧有可能造成死锁，唯一区别：它会抛出原始异常而不是被包装成的 AggregateException。
FooAsync().GetAwaiter().GetResult();
```

### 唯一区别

**GetAwaiter().GetResult()** 会抛出原始异常而不是被包装成的 AggregateException
- 此外，这种写法在 async Task Main （异步入口函数）源码中被使用，因此并非见不得光

### 风险

#### 1. 阻塞

这两种写法均为阻塞等待，仍为同步代码

#### 2. 死锁风险

当在 UI 线程或 ASP.NET 请求上下文中调用 .Wait() 或 .Result() 时，如果异步方法内部需要回到原始上下文（例如，使用 await 后续代码需要在 UI 线程上执行），但该上下文也正在阻塞等待异步方法，就会导致死锁。

## 4. 方案二：Fire-and-Forget

对应示例：[2_FireAndForget/Program.cs](../../../Code/CSharp进阶/多线程与异步/6_在同步方法中非阻塞地调用异步方法/2_FireAndForget/Program.cs)

典型写法：

```csharp

try
{
    //2.1 对于 async Task 标记的方法，外部无法捕获异常，主线程无报错
    _ = FooAsync(); //使用弃元写法避免警告

    //2.2 对于 async Void 标记的方法，程序直接崩溃
    VoidFooAsync();

    //主线程不会等待 FooAsync 方法，因此会直接输出 Hello, World! 后结束程序
    Console.WriteLine("Hello, World!");
}
catch (Exception ex)
{
	//无论上面哪种写法，都无法正确捕获异常
    Console.WriteLine(ex);
    throw;
}

```

### 优点

- 不阻塞当前线程
- 写法简单

### 缺点

#### 1.  对于`async Task` ，异步任务出异常时外层抓不到，无任何提示

#### 2. 对于`async void`，异步任务出异常时会直接导致程序崩溃

### 结论

裸 Fire and Forget 只能说“看起来不阻塞”，但异常、生命周期、完成时机都不受控，通常不应该直接使用。

## 5. 方案三：以回调函数包装 Fire-and-Forget

对应示例：[3_CallBack/Program.cs](../../../Code/CSharp进阶/多线程与异步/6_在同步方法中非阻塞地调用异步方法/3_CallBack/Program.cs)

思路：使用回调思想包装一发即忘，在异步任务的线程处理异常、做完成通知

### 方法一：静态方法包装

```csharp
//3.1 使用回调方法对一发即忘进行包装，正确地处理异常
static async void SafeFireAndForget(Task task, Action? onCompleted = null, Action<Exception>? onError = null)
{
    //这里处于异步线程，在这正确处理异常可以避免程序崩溃
    try
    {
        await task;
        onCompleted?.Invoke();  //异步任务正常完成，执行完成动作
    }
    catch (Exception ex)
    {
        onError?.Invoke(ex);
    } 
}
```

调用：

```csharp
SafeFireAndForget(LoadDataAsync(), () => IsDataLoaded = true, e => throw e);
```

### 方法二：扩展方法包装

```csharp
//3.2 将回调方法包装为 Task 类的扩展

static class TaskExtensions
{
    public static async void SafeAwait(this Task task, Action? onCompleted = null, Action<Exception>? onError = null)
    {
        try
        {
            await task;
            onCompleted?.Invoke();
        }
        catch (Exception ex)
        {
            onError?.Invoke(ex);
        }
    }
}
```

调用：

```csharp
LoadDataAsync().SafeAwait(() => IsDataLoaded = true, e => throw e);
```

### 这个方案解决了什么

- 不阻塞主线程
- 程序不会因为 `async void` 出异常而崩溃
- 可以在异步任务的线程捕获异常，集中处理日志、提示等信息
- 可以在异步正常完成时触发完成动作

### 依然没解决什么

- 异常实际上实在异步线程侧集中处理，外层依然拿不到异步任务的结果（如是否完成、取消等）
- 外层`try/catch` 依然抓不到内部异步异常
- 本质上依旧是对 `async void` 型一发即忘的包装，只是“更安全”，不是“可等待”

### 适用场景

适合下面这类“启动一个后台异步任务即可”的场景：

1.  构造函数里触发后台预加载
2. 某些初始化动作不要求调用方立即拿到结果
3. 只要求记录异常，不要求向上抛出

这是一个实用的过渡方案，但不是最理想的架构方案。

## 6. 方案四：`ContinueWith` 包装一发即忘

对应示例：[4_ContinueWith/Program.cs](../../../Code/CSharp进阶/多线程与异步/6_在同步方法中非阻塞地调用异步方法/4_ContinueWith/Program.cs)

典型写法：

```csharp
LoadDataAsync().ContinueWith(OnDataLoaded, TaskScheduler.Default);

//ContinueWith 只能传入一个回调委托，因此这里将需要做的事全都包装在一个委托内
private bool OnDataLoaded(Task task)
{
    if (task.IsFaulted)
    {
        //这里使用 InnerException 拿到内部异常，否则拿到的是 AggregateException
        Console.WriteLine(task.Exception.InnerException.Message);
    }
    return IsDataLoaded = true;
}
```
示例中通过 `task.IsFaulted` 和 `task.Exception.InnerException` 处理异常

### 优点

- 不阻塞当前线程
- 可以在 continuation 中同意检查任务状态
- 不会像裸 Fire and Forget 那样完全失去对异常的观察

### 缺点

- `ContinueWith` 一定会将传入的委托包装成一个 `Task`，即便该委托不是异步任务，这样会导致额外消耗
- `ContinueWith` 的 `TaskScheduler`(控制后续任务在哪个线程上完成) 的默认值为 `TaskScheduler.Current`，而非 `TaskScheduler.Default`，这样可能会有死锁风险

### 关键注意点

#### 1. 调度器要显式指定

示例里特意写了：
```csharp
TaskScheduler.Default
```

原因：`ContinueWith` 默认使用的调度语义容易让人误判上下文，尤其在 UI 或特殊同步上下文里，可能引入额外复杂度甚至死锁风险。

#### 2.  额外开销

即便 continuation 里只是同步委托，也会被包装成一个新的 `Task`，有额外心智负担和一定调度开销。

### TODO：额外拓展（待补充）

- [`ContinueWith` 方法实现单元测试](https://www.youtube.com/watch?v=vYXs--S0Xxo)

### 结论

> `ContinueWith` 比裸 Fire and Forget 更可控，但一般更像底层工具，而不是首选业务写法。如果能用 `await` 重构，优先还是重构。

## 7. 方案五：异步工厂替代类的构造函数

对应示例：[5_AsyncFactory/Program.cs](../../../Code/CSharp进阶/多线程与异步/6_在同步方法中非阻塞地调用异步方法/5_AsyncFactory/Program.cs)

### 解决的问题

> 构造函数里需要执行异步初始化，但构造函数本身不能 `await`

### 核心思路

1. 构造函数私有化
2. 提供 `CreateAsync()` 工厂方法
3. 在工厂方法里先 `new`，再 `await InitAsync()`进行异步初始化
4. 调用方拿到的是“初始化完成后的对象”

典型写法：

```csharp
class MyService
{
    public bool IsServiceCreated { get; private set; } = false;

    //私有构造
    private MyService()
    {

    }

    async Task InitAsync()
    {
        await Task.Delay(1000);
    }

    //使用工厂模式，就可以在外层 await CreateAsync() 拿到已经创建好的类对象
    public static async Task<MyService> CreateAsync()
    {
        var service = new MyService();
        await service.InitAsync();
        
        //throw new Exception();
        service.IsServiceCreated = true;
        return service;
    }
}
```

调用方：

```csharp
internal class Program
{

    //注意：这里是异步入口函数
    //异步入口函数在编译时会自动创建普通的 Main 函数，然后在其中使用 .GetAwaiter().GetResult() 的方式调用异步任务
    static async Task Main(string[] args)
    {
        var myService = await MyService.CreateAsync();
        Console.WriteLine($"Service is Created: {myService.IsServiceCreated}");
    }
}
```

### 缺点：

1. 没办法注册给 IOC 容器
2. 不方便实现单例

### 针对缺点的补充方案：
 
 1. 注册 IOC 容器: Microsoft.Extensions.DependencyInjection
 2. 实现单例: AsyncLazy: Nito.AsyncEx, Microsoft.VisualStudio.Threading
 3. Task工厂: JoinableTaskFactory: Microsoft.VisualStudio.Threading
 4. 单元测试: Microsoft.VisualStudio.TestTools.UnitTesting

## 8. 方案六：WPF中异步绑定到事件或命令

对应示例：[6_AsyncLoadForWPF/MainWindow.xaml](../../../Code/CSharp进阶/多线程与异步/6_在同步方法中非阻塞地调用异步方法/6_AsyncLoadForWPF/MainWindow.xaml)

这是 UI 场景下最值得采用的思路：

> 不要在同步方法里“假装等待异步”，而是让 UI 生命周期天然承接异步。

### 优点：

- 可以直接绑定加载中状态
- 可以控制按钮禁用、Loading 动画、状态文案
- UI 能正确反映异步任务生命周期

### 方法一：在窗体的`Loaded` 事件里调异步方法

窗口先显示，数据后台加载，不会卡UI

xaml：
```xml
<Loaded="Window_Loaded">
```

xaml.cs：
```csharp
public partial class MainWindow : Window
{
    private ViewModel _viewModel;

    public MainWindow()
    {
        InitializeComponent();
        _viewModel = new ViewModel();
        this.DataContext = _viewModel;
    }

    //1. 在 Loaded 事件中调用 ViewModel 的异步加载数据方法 (需要在 xaml 中注明 Loaded="Window_Loaded" 事件)
    private async Task Window_Loaded(object sender, RoutedEventArgs e)
    {
        await _viewModel.LoadDataAsync();
    }
}
```

### 方法二：MVVM 中过命令绑定 Loaded

#### 1. 手动声明 AsyncRelayCommand

ViewModel：

```csharp
internal class ViewModel
{
    //2. 使用 EventToCommand 绑定 Loaded 事件到 Command (需要在 xaml 中使用 EventTrigger、InvokeCommandAction)

    //2.1 手搓 IAsyncRelayCommand
    public IAsyncRelayCommand LoadDataommand { get; }

    public ViewModel()
    {
        //2.1 手动声明 AsyncRelayCommand
        LoadDataCommand = new AsyncRelayCommand(LoadDataAsync);
    }

    public async Task LoadDataAsync()
    {
        await Task.Delay(1500);
    }
}
```

View：

```xml
<!--需安装 Microsoft.Xaml.Behaviors.Wpf 包，并且在 Window 中注明 xmlns:i="http://schemas.microsoft.com/xaml/behaviors"-->

<i:Interaction.Triggers>
    <i:EventTrigger EventName="Loaded">
        <i:InvokeCommandAction Command="{Binding LoadDataCommand}" />
    </i:EventTrigger>
</i:Interaction.Triggers>

<Grid>
    <DockPanel LastChildFill="False">
        <TextBlock Text="Data is loading: " />
        <!--绑定 AsyncRelayCommand 的 IsRunning-->
        <TextBlock Text="{Binding LoadDataCommand.IsRunning}" />
    </DockPanel>
</Grid>
```

#### 特点：控件可以直接绑定 `AsyncRelayCommand` 的属性，如 `IsRunning`


#### 2. 使用 CommunityToolkit 提供的 RelayCommand

ViewModel：

```csharp
internal partial class ViewModel : ObservableObject
{

    //2. 使用 EventToCommand 绑定 Loaded 事件到 Command (需要在 xaml 中使用 EventTrigger、InvokeCommandAction)

    public ViewModel()
    {
       
    }

    //2.2 使用 CommunityToolkit 自带的 RelayCommand
    //对于 Prism, 原生的 DelegateCommand 更偏向同步命令，如果项目里大量存在异步命令，可以自己封装一个 AsyncDelegateCommand

    [RelayCommand]  //同步异步皆可用，异步方法时，框架会自动生成 IAsyncRelayCommand 类型的 Command
    public async Task LoadDataAsync()   //注：RelayCommand生成的命令名会自动去除末尾的 Async，因此 xaml 中应该绑定 LoadDataCommand
    {
        await Task.Delay(1500);
    }
}
```

View 与 *手动声明 `AsyncRelayCommand`* 完全相同

#### 扩展：使用 CommunityToolkit 提供的 TaskNotifier

>*`TaskNotifier`本质是 `Task` 的包装器，可以用来监视异步操作的状态（如是否正在运行、是否完成、是否有异常等）*

如：前台某些控件的显示状态与 Task.IsRunning 进行绑定（AsyncRelayCommand 本身也有 IsRunning 属性可供绑定）

##### 关键：
	1. 当 Task 完成时，它会再次触发 PropertyChanged
	2. 需要配合 SetPropertyAndNotifyOnCompletion 使用

##### 解决的问题：
- 普通的 `Task` 完成时不会触发 `PropertyChanged`，UI无法自动刷新，而 `TaskNotifier` 能自动监听异步任务完成并触发 `PropertyChanged`。


## 9. 六种方案对比

| 方案                          | 是否阻塞当前线程  | 异常是否容易处理       | 适用场景    |
| --------------------------- | --------- | -------------- | ------- |
| `Wait()` / `Result`         | 是         | 一般，且有死锁风险      | 不推荐     |
| `GetAwaiter().GetResult()`  | 是         | 比较直观，但仍有死锁风险   | 不推荐     |
| 裸 Fire and Forget           | 否         | 差，容易丢异常        | 不推荐     |
| 回调包装 / `SafeAwait`          | 否         | 较好，可在异步侧集中处理   | 过渡可用    |
| `ContinueWith`              | 否         | 可控，但复杂         | 特定场景可用  |
| 异步工厂                        | 否         | 好，可正常 `await`  | 类构造     |
| WPF 异步命令 / 事件绑定             | 否         | 好，且符合 UI 模型    | WPF异步加载 |

## 10.  结语

> “在同步方法中非阻塞地调用异步方法”本身往往意味着设计受限，不如直接拥抱异步编程

 * 异步编程生态：
 *      1. async Task Main      : 入口异步
 *      2. async void           : 委托注册
 *      3. Asynclazy            : 异步单例
 *      4. IAsyncEnumerable     : 异步数据流
 *      5. IAsyncDisposable     : 异步释放资源
 *      6. AsyncRelayCommand    : 异步绑定

这些能力组合起来，才是现代 C# 异步编程的完整生态。
