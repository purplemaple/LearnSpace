# 数据库学习路线：从基础复盘到面试进阶

## 1. 问题背景

我已经学过一部分数据库知识，因此这条路线不再按零基础教程推进。

后续学习重点需要调整为：

1. 基础知识快速复盘，不把时间花在已经熟悉的 CRUD 和工具操作上。
2. 弱化 PostgreSQL 绑定，把 PostgreSQL 作为本机练习环境，而不是学习目标本身。
3. 弱化“C# 如何连接数据库”“ORM 如何配置”这类公式化内容。
4. 聚焦 SQL 通用能力、索引、执行计划、事务、锁、并发、慢查询排查和面试表达。
5. 按每天至少 6 小时的节奏推进，用高强度实操防止学了就忘。

这里需要注意的是，不同数据库在语法、执行计划格式、锁实现、隔离级别细节上会有差异。但面试和工作里真正高频的能力通常是共通的：

- 查询语义是否清楚。
- 表结构是否合理。
- 索引是否建在真正有价值的访问路径上。
- 能否根据执行计划判断慢在哪里。
- 能否解释事务隔离和并发异常。
- 能否把数据库问题和业务场景连起来。

本机 PostgreSQL 18.x 只作为实验载体。路线中会尽量把“通用结论”和“PostgreSQL 实验写法”分开。

这条路线建议按 18 天核心冲刺推进，之后再用 7 天做面试复盘和弱点补齐。

## 3. 每天 6 小时学习节奏

建议每天按下面节奏执行：

1. **第 1 小时：概念复盘**
   - 只看核心结论。
   - 不做大段摘抄。
   - 明确今天要验证的数据库现象。

2. **第 2 到 4 小时：SQL 实验**
   - 运行脚本。
   - 改查询条件。
   - 对比执行计划和耗时。
   - 记录“为什么结果是这样”。

3. **第 5 小时：面试表达**
   - 把实验结果转换成面试回答。
   - 按“结论 -> 原理 -> 例子 -> 风险边界”组织。

4. **第 6 小时：复盘和自测**
   - 不看答案重写核心 SQL。
   - 写 3 到 5 个自测问题。
   - 记录一个最容易忘的坑。

如果当天状态好，可以把第 6 小时改成模拟面试。

## 4. 学习环境定位

### 4.1 目录边界

当前目录约定：

- `Note\DataBase`：路线、笔记、复盘、面试题、实验结论。
- `Code\DataBase`：只放 SQL、脚本、示例项目等代码相关文件。

后续和我对话学习时，如果需要新增说明性内容，应放到 `Note\DataBase`；如果需要新增可执行 SQL，应放到 `Code\DataBase`。

### 4.2 本机数据库的作用

PostgreSQL 只承担三个作用：

1. 提供可运行的 SQL 实验环境。
2. 用 `EXPLAIN` / `EXPLAIN ANALYZE` 观察执行计划。
3. 用两个连接窗口模拟事务、锁等待和死锁。

不要把路线学偏成“PostgreSQL 工具教程”。

需要区分：

| 内容 | 是否通用 | 说明 |
| --- | --- | --- |
| `JOIN`、聚合、子查询 | 高度通用 | 各数据库语法差异较小 |
| B+Tree 索引思想 | 高度通用 | 具体执行计划格式不同 |
| 事务 ACID | 高度通用 | 实现细节不同 |
| 隔离级别现象 | 比较通用 | 各数据库默认级别和 MVCC 实现不同 |
| `EXPLAIN ANALYZE` | 工具有差异 | 思路通用，输出不通用 |
| `generate_series` | PostgreSQL 特有 | 只用于造测试数据 |
| `FreeSql` / `EF Core` | 岗位加分项 | 本路线只保留边界认知 |

## 6. 第一阶段：SQL 查询强化

### 6.1 学习目标

这个阶段不是练增删改查，而是训练复杂查询能力。

重点：

- 多表连接。
- 聚合统计。
- 条件聚合。
- 子查询。
- 公共表表达式。
- 窗口函数。
- Top N。
- 去重和查重。
- 分页。

### 6.2 必做题型

每天至少完成 20 道查询题，题型覆盖：

1. 查询每个设备最近一次运行记录。
2. 查询每个设备成功率。
3. 查询报警次数 Top 10。
4. 查询连续失败超过 3 次的设备。
5. 查询每个设备最近 7 天的运行趋势。
6. 查询重复业务编号。
7. 查询有运行记录但没有步骤明细的批次。
8. 查询每个设备耗时最长的一次运行。
9. 查询每类报警首次出现和最后出现时间。
10. 查询每个设备按时间排序后的前后两次运行间隔。

### 6.3 窗口函数必须掌握

至少掌握：

- `ROW_NUMBER()`
- `RANK()`
- `DENSE_RANK()`
- `LAG()`
- `LEAD()`
- `SUM() OVER`
- `COUNT() OVER`

窗口函数的价值在于：它可以在不提前把明细聚合掉的情况下，拿到排名、前后行、累计值等信息。

典型场景：

```sql
SELECT
    device_id,
    batch_code,
    status,
    started_at,
    ROW_NUMBER() OVER (
        PARTITION BY device_id
        ORDER BY started_at DESC
    ) AS rn
FROM test_batches;
```

面试表达：

> 普通 `GROUP BY` 会把多行压缩成一行，窗口函数是在保留明细行的同时计算排名、累计、前后差值。遇到“每组最新一条”“每组 Top N”“前后两次间隔”这类问题时，窗口函数通常比在应用层循环更清晰。

## 7. 第二阶段：表设计与数据一致性

### 7.1 学习目标

表设计不是背范式，而是判断数据应该放在哪里、如何避免后续查询和维护痛苦。

重点：

- 一对一、一对多、多对多。
- 主键和业务唯一键。
- 外键是否一定要建。
- 历史快照。
- 字典表。
- 审计日志。
- 范式和反范式取舍。

### 7.2 必做建模题

至少完成下面 5 个建模题：

1. 设备运行记录系统。
2. 订单、订单明细、支付、退款系统。
3. 用户、角色、权限系统。
4. 文章、标签、评论系统。
5. 仓库库存流水系统。

每个建模题都要回答：

1. 核心实体有哪些？
2. 哪些是一对多？
3. 哪些是多对多？
4. 主键用什么？
5. 业务唯一约束是什么？
6. 哪些字段需要历史快照？
7. 哪些查询会最频繁？
8. 哪些字段未来可能导致索引或锁问题？

### 7.3 面试判断口径

不要把“符合第三范式”当作万能答案。

更合适的说法是：

> 默认先保持关系清晰，减少重复数据；如果某些报表或查询路径非常高频，再考虑有控制地反范式化。反范式不是为了偷懒，而是用冗余换查询性能，同时要承担数据一致性维护成本。

## 8. 第三阶段：索引与执行计划

### 8.1 学习目标

这是本路线的核心。

需要掌握：

- B+Tree 索引基本结构。
- 聚集索引和非聚集索引的差异。
- 主键索引、唯一索引、普通索引。
- 单列索引、联合索引。
- 最左前缀原则。
- 覆盖索引。
- 回表。
- 索引选择性。
- 排序和索引的关系。
- 分页优化。
- 慢查询排查流程。

### 8.2 通用优化判断

慢查询不要上来就说“加索引”。

排查顺序：

1. 确认 SQL 和参数是否符合预期。
2. 确认数据量和返回行数。
3. 查看执行计划。
4. 判断是否全表扫描。
5. 判断过滤条件是否有合适索引。
6. 判断排序是否额外产生昂贵操作。
7. 判断是否存在回表、临时表、文件排序等代价。
8. 判断分页是否过深。
9. 判断是否一次查了太多列或太多行。
10. 优化后用执行计划和耗时对比验证。

### 8.3 必做实验

围绕同一张大表做实验：

1. 无索引条件查询。
2. 单列索引查询。
3. 联合索引查询。
4. 联合索引列顺序对比。
5. 覆盖索引对比。
6. 范围查询对排序的影响。
7. `LIKE 'abc%'` 和 `LIKE '%abc%'` 对比。
8. 函数包列导致索引失效。
9. 深分页和游标分页对比。
10. 低选择性字段索引效果对比。

### 8.4 面试高频回答模板

问题：为什么建立了索引还是慢？

回答思路：

1. 索引可能没有被使用，例如查询条件不符合索引列顺序。
2. 即使用了索引，返回数据量太大也可能慢。
3. 查询列太多可能需要大量回表。
4. 排序字段和过滤字段不匹配，仍然需要额外排序。
5. 统计信息不准确时，优化器可能选错计划。
6. 深分页会扫描并丢弃大量数据。
7. 锁等待、IO 压力、网络传输、应用层渲染也可能让用户感知为“查询慢”。

## 9. 第四阶段：事务、锁与并发

### 9.1 学习目标

这是面试和实际排障的第二个核心。

需要掌握：

- ACID。
- 脏读、不可重复读、幻读。
- Read Committed、Repeatable Read、Serializable。
- MVCC 基本思想。
- 行锁、表锁、间隙锁概念。
- 乐观锁、悲观锁。
- 锁等待。
- 死锁。
- 长事务风险。

### 9.2 事务边界判断

这里需要注意的是，数据库事务不等于业务流程。

例如设备执行一次动作可能持续几十秒甚至几分钟，但数据库事务不应该一直包住整个设备动作。

更合理的方式：

1. 批次开始时写入一条记录并提交。
2. 每个步骤完成后追加步骤结果。
3. 出错时记录失败原因。
4. 最终更新批次状态。
5. 使用状态机或补偿机制保证业务可追踪，而不是用长事务强行包住外部设备动作。

面试表达：

> 事务适合保护短时间内必须同时成功或失败的数据修改，不适合包住长时间的外部 IO、设备动作或人工操作。长事务会占用锁和版本资源，增加阻塞和死锁风险。

### 9.3 必做并发实验

至少完成：

1. 两个事务同时更新同一行，观察锁等待。
2. 一个事务读，另一个事务改，观察隔离级别差异。
3. 两个事务交叉更新两行，制造死锁。
4. 用版本号字段模拟乐观锁。
5. 用 `SELECT ... FOR UPDATE` 模拟悲观锁。
6. 保持一个长事务不提交，观察它对其他操作的影响。

### 9.4 面试高频回答模板

问题：线上出现死锁怎么办？

回答思路：

1. 先拿到死锁日志或数据库提供的锁等待信息。
2. 找出参与死锁的 SQL、事务和访问表。
3. 检查两个事务是否以不同顺序访问相同资源。
4. 缩短事务时间，减少事务内无关操作。
5. 保证多处代码按固定顺序访问表或行。
6. 给过滤条件补合适索引，避免锁范围扩大。
7. 必要时加入重试，但重试不能替代根因修复。

## 11. C#、ORM 与工具知识如何处理

### 11.1 降低优先级

C# 连接数据库、ORM 配置、连接字符串、依赖注入这些内容对工程落地有价值，但不是当前数据库面试核心。

因此路线中只保留下面要求：

1. 知道参数化查询用于避免 SQL 注入。
2. 知道连接、事务、命令对象需要控制生命周期。
3. 知道同步数据库调用会阻塞 UI 线程。
4. 知道 ORM 可能产生 N + 1、复杂 SQL、懒加载问题。
5. 能说出复杂统计或性能敏感场景可以回到手写 SQL。

### 11.2 面试口径

如果被问 ORM：

> ORM 可以提升普通 CRUD 的开发效率，但不能替代数据库理解。遇到复杂查询、慢查询、批量写入、报表统计时，我会先观察 ORM 生成的 SQL，再根据执行计划判断是否需要优化查询、补索引，或者改为手写 SQL。

## 13. 7 天复盘补强

复盘阶段不要再扩大量，而是修薄弱点。

每天固定做：

1. 重写 10 条 SQL。
2. 复述 5 道面试题。
3. 看 2 个执行计划。
4. 做 1 个并发或锁实验。
5. 写 1 条最终面试表达。

## 14. 和我对话学习时的推进方式

后续每一步可以按这个节奏来：

1. 我先给你一个主题和目标。
2. 你先尝试回答或写 SQL。
3. 我指出问题、补充原理、给出更好的表达。
4. 必要时我直接补充实验脚本或修改练习环境。
5. 最后把本节内容沉淀到 `Note\DataBase`。

每个主题都按下面结构收束：

```markdown
## 1. 问题背景

## 2. 结论

## 3. 实验过程

## 4. 关键现象

## 5. 风险和边界

## 6. 面试表达
```

这样学习不会停留在“我看过”，而是每一步都有实验、复盘和面试转化。
