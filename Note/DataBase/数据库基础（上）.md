## 1. SQL 中 JOIN 的类型？区别是什么？

**答案要点（面试可直接说）：**
- **INNER JOIN**：返回两个表中匹配的行（交集）。
- **LEFT (OUTER) JOIN**：返回左表所有行，以及右表匹配行；右表不匹配时为 NULL。
- **RIGHT (OUTER) JOIN**：返回右表所有行，以及左表匹配行；左表不匹配时为 NULL。
- **FULL (OUTER) JOIN**：返回左右表所有行，匹配的合并，不匹配的补 NULL（并集）。
- **CROSS JOIN**：笛卡尔积，返回左表行数 × 右表行数。
- **SELF JOIN**：同表之间的 JOIN，可用别名实现。

**面试深入点/常见追问：**
- `LEFT JOIN ... WHERE rightTable.col IS NULL` 用来找左表中没有匹配右表的行（反向查找/缺失项）。
- `LEFT JOIN` 与把条件放到 `ON` 或 `WHERE` 的差异：若把过滤条件放在 `WHERE`，会把非匹配行过滤掉，可能失去 `LEFT JOIN` 的效果。

**示例 SQL：**
```sql
-- INNER JOIN
SELECT a.Id, a.Name, b.OrderId
FROM Users a
INNER JOIN Orders b ON a.Id = b.UserId;

-- LEFT JOIN（找出没有订单的用户）
SELECT a.Id, a.Name
FROM Users a
LEFT JOIN Orders b ON a.Id = b.UserId
WHERE b.OrderId IS NULL;
```

## 2. 主键 (Primary Key)、外键 (Foreign Key)、唯一索引 (Unique) 的区别？

**答案要点：**
- **主键（Primary Key）**
  - 唯一标识一行记录，不能为 NULL（在多数 DBMS 中）。
  - 经常与聚集索引绑定（例如 SQL Server 默认）。
  - 一个表只有一个主键（可以是复合主键）。
- **外键（Foreign Key）**
  - 在一个表中引用另一个表的主键（或唯一键），用于维护参照完整性。
  - 可以定义级联行为（ON DELETE CASCADE / ON UPDATE CASCADE）。
- **唯一索引 / 唯一约束（UNIQUE）**
  - 保证列或列组合的值唯一，但允许 NULL（行为依 DBMS 可能不同）。
  - 与主键的不同：表可以有多个唯一索引，但只有一个主键。

**示例 SQL：**
```sql
CREATE TABLE Users (
  Id INT PRIMARY KEY,
  Email NVARCHAR(200) UNIQUE
);

CREATE TABLE Orders (
  OrderId INT PRIMARY KEY,
  UserId INT,
  CONSTRAINT FK_Orders_Users FOREIGN KEY (UserId) REFERENCES Users(Id)
);
```

**面试加分点：**
- 什么时候用唯一索引而不用主键？（例如：需要多列保持唯一性，但主键已被占用）
- 外键会带来性能与删除复杂性（级联删除风险）——要权衡数据完整性 vs 性能/复杂性。

## 3. 聚集索引（Clustered）和非聚集索引（Non-clustered）有什么区别？如何选择？

**核心要点：**
- **聚集索引（Clustered Index）**
  - 表中数据的物理存储顺序按照聚集索引键排序。
  - 每表最多一个聚集索引。
  - 适合范围查询（`BETWEEN`、`ORDER BY`、`GROUP BY` 等）。
- **非聚集索引（Non-Clustered Index）**
  - 另建一棵索引树，索引记录指向数据行（或聚集索引键）。
  - 可有多个非聚集索引。
  - 适合点查（精确匹配）。
- **覆盖索引（Covering Index）**
  - 索引包含查询所需的所有列，避免回表（提高性能）。

**选择原则：**
- 将频繁用于排序或范围查询且选择性高的字段建聚集索引（例如时间戳、主键）。
- 将常用于 WHERE 精确匹配或作为 JOIN 条件的列建非聚集索引。
- 避免给低选择性列（例如布尔）建索引。

**面试常见追问：**
- 聚集索引变更（更新聚集索引键）成本大，会引起页移动。
- 如何查看索引使用情况？（用 DBMS 的执行计划 / DMVs）

## 4. SQL 常见约束（Constraints）有哪些？作用是什么？

**常见约束：**
- `NOT NULL`：列不允许为 NULL。
- `UNIQUE`：列值唯一。
- `PRIMARY KEY`：唯一且非 NULL，标识行。
- `FOREIGN KEY`：参照完整性，引用另表的列。
- `CHECK`：自定义表达式约束（例如 CHECK(age >= 0)）。
- `DEFAULT`：默认值。

**示例 SQL：**
```sql
CREATE TABLE Product (
  Id INT PRIMARY KEY,
  Name NVARCHAR(100) NOT NULL,
  Price DECIMAL(10,2) NOT NULL CHECK (Price >= 0),
  CreatedAt DATETIME DEFAULT GETDATE()
);
```

**面试要点：**
- 约束和索引的关系：`PRIMARY KEY` 与 `UNIQUE` 通常会建立索引。
- 约束有助于保证数据完整性，但过多约束会影响写入性能。

## 5. 数据库范式（Normalization）是什么？1NF/2NF/3NF 概念及为何有时需要反范式（denormalization）？

**简明解释：**
- **范式** 是数据库设计中用以减少冗余和异常（插入/更新/删除异常）的规则集合。
- 常见范式：
  - **1NF（第一范式）**：每列原子性，列中不可再分。
  - **2NF（第二范式）**：在 1NF 的基础上，消除部分依赖（适用于复合主键）。
  - **3NF（第三范式）**：在 2NF 的基础上，消除传递依赖（非主属性不依赖于其它非主属性）。

**为什么有时需要反范式：**
- 为了提高查询性能，减少 JOIN 操作的成本，可能会引入冗余字段（例如缓存某些汇总值）。
- OLTP 系统倾向规范化；OLAP / 报表 / 高并发读取场景常常采用反范式或增加物化视图 / 缓存。

**面试讨论点：**
- 举例说明什么时候做反范式（例如订单表里冗余用户昵称以减少 JOIN）。
- 如何保证反范式数据的一致性？（事务、触发器、后台同步 job）

## 6. ADO.NET、Dapper、EF Core 各自适用场景与区别（简要对比并给出示例）？

**对比要点：**

- **ADO.NET（原生）**
  - 最底层的数据访问方式： `DbConnection`、`DbCommand`、`DbDataReader`。
  - 优点：性能稳定、可完全控制 SQL 和连接细节。
  - 缺点：样板代码多，开发效率低。

- **Dapper**
  - 轻量级微 ORM（由 StackExchange 提供）。
  - 优点：几乎和 ADO.NET 性能一致，写 SQL，但支持对象映射，代码量少。
  - 适合：性能敏感且需要 SQL 控制的场景。

- **EF Core**
  - 完整 ORM，支持 LINQ、迁移（Migrations）、变更追踪。
  - 优点：开发效率高、适合业务开发节省时间。
  - 缺点：抽象带来性能开销（可通过优化缓解）。

**示例：同一查询的三种实现**

- ADO.NET（示例）
```csharp
using var conn = new System.Data.SqlClient.SqlConnection(connStr);
using var cmd = conn.CreateCommand();
cmd.CommandText = "SELECT Id, Name FROM Users WHERE Id = @id";
cmd.Parameters.AddWithValue("@id", id);
conn.Open();
using var reader = cmd.ExecuteReader();
if (reader.Read())
{
    var name = reader.GetString(1);
}
```

- Dapper（示例）
```csharp
using var conn = new System.Data.SqlClient.SqlConnection(connStr);
var user = conn.QuerySingleOrDefault<User>("SELECT Id, Name FROM Users WHERE Id = @id", new { id });
```

- EF Core（示例）
```csharp
var user = context.Users.AsNoTracking().SingleOrDefault(u => u.Id == id);
```

**面试回答建议：**
- 根据场景选择工具：读多写少且性能关键用 Dapper/ADO.NET；业务开发快速迭代用 EF Core。

## 7. EF Core 的 Include 会带来哪些问题？怎么优化？

**问题来源：**
- `Include` 导致 EF Core 生成 JOIN 或多次查询以加载关联实体，可能产生下面问题：
  - 大量 JOIN 导致数据重复返回（笛卡尔样式展开）；
  - 传输过多字段（SELECT *）；
  - 性能下降与内存占用增加。

**优化方法：**
- 使用 `Select` 投影（projection）只取需要字段：  
  ```csharp
  var list = context.Orders
      .Where(o => o.Status == status)
      .Select(o => new {
          o.Id,
          o.CreatedAt,
          UserName = o.User.Name,
          Items = o.Items.Select(i => new { i.Sku, i.Quantity })
      })
      .ToList();
  ```
- 使用 `AsNoTracking()` 如果只读，禁用 ChangeTracker。
- 使用 `AsSplitQuery()` 将单个多表查询拆成多次查询（适用于 1:N 的 Include 导致笛卡尔展开）。
- 为频繁访问的组合使用视图或缓存。

**示例（Include 可能导致问题）**
```csharp
// 可能会返回重复的 Order 行，因为每个 OrderItem 都会展开
var orders = context.Orders
    .Include(o => o.Items)
    .Include(o => o.User)
    .ToList();
```

## 8. EF Core 的 ChangeTracker 是什么？为什么会影响性能？如何在查询中禁用它？

**解释：**
- **ChangeTracker**：EF Core 用于跟踪从数据库查询回来的实体状态（Added、Modified、Unchanged、Deleted），以便 `SaveChanges()` 能生成更新语句。
- **性能影响**：当查询大量数据时，ChangeTracker 要为每个实体维护元数据与状态，消耗内存和 CPU。

**禁用办法（只读查询推荐）：**
- 对查询使用 `AsNoTracking()`：
```csharp
var users = context.Users.AsNoTracking().Where(u => u.IsActive).ToList();
```
- 对整个上下文设置默认跟踪行为（不推荐长期使用）：
```csharp
context.ChangeTracker.QueryTrackingBehavior = QueryTrackingBehavior.NoTracking;
```

**面试常问点：**
- 什么时候不能使用 `AsNoTracking()`？（当需要对实体进行编辑并调用 SaveChanges 时不能）
- `AsNoTrackingWithIdentityResolution()` 在某些场景下能保留引用相等性同时减少跟踪开销。

## 9. 如何防止 SQL 注入？请给出 C# 示例。

**关键做法：**
1. **使用参数化查询**（永远不要把用户输入拼接到 SQL）。
2. 使用 ORM（如 EF Core）默认会参数化大多 LINQ 查询。
3. 对输入进行严格验证与白名单过滤（尤其对对象名、列名等动态 SQL）。
4. 最小化数据库权限（原则：最小权限）。

**ADO.NET 参数化查询示例：**
```csharp
string sql = "SELECT Id, Name FROM Users WHERE Name = @name AND Age >= @minAge";
using var conn = new System.Data.SqlClient.SqlConnection(connStr);
using var cmd = new System.Data.SqlClient.SqlCommand(sql, conn);
cmd.Parameters.AddWithValue("@name", userInputName);
cmd.Parameters.AddWithValue("@minAge", minAge);
conn.Open();
using var reader = cmd.ExecuteReader();
```

**EF Core（LINQ）示例：**
```csharp
var q = context.Users.Where(u => u.Name == userInputName && u.Age >= minAge).ToList();
```
（EF Core 会把参数转为 SQL 参数，从而避免注入）

**注意事项：**
- `AddWithValue` 虽方便，但有时会导致参数类型推断问题，推荐显式构造参数并指定类型与长度以避免隐式转换导致索引失效：
```csharp
cmd.Parameters.Add(new SqlParameter("@name", SqlDbType.NVarChar, 100) { Value = userInputName });
```

## 10. DataReader 与 DataSet 的区别？什么时候使用哪个？

**区别：**

- **DataReader**
  - 前向只读流（forward-only），基于连接（connected）。
  - 性能高，内存占用少。
  - 适用于读取大量数据并逐行处理的场景（例如批处理、导出）。
  - 使用后需及时关闭连接和释放资源。

- **DataSet / DataTable**
  - 断开连接（disconnected）设计，数据被加载到内存中。
  - 支持多表、关系、数据修改和离线处理，常配合 `DataAdapter` 使用。
  - 适合需要在内存中操作数据（修改、关系、序列化）的场景，但内存占用高。

**示例对比：**

- DataReader 使用（适合大批量只读）：
```csharp
using var conn = new SqlConnection(connStr);
using var cmd = new SqlCommand("SELECT Id, Name FROM Users", conn);
conn.Open();
using var reader = cmd.ExecuteReader();
while (reader.Read())
{
    int id = reader.GetInt32(0);
    string name = reader.GetString(1);
    // 逐行处理
}
```

- DataSet 使用（适合离线编辑）：
```csharp
using var conn = new SqlConnection(connStr);
var adapter = new SqlDataAdapter("SELECT Id, Name FROM Users", conn);
var ds = new DataSet();
adapter.Fill(ds, "Users");
DataTable users = ds.Tables["Users"];
// 修改 users，之后用 SqlCommandBuilder + adapter.Update(ds,"Users") 提交（复杂）
```

**面试要点：**
- 如果面试官问内存/性能选择：当需要高性能逐行读取时选 `DataReader`，当需要在 UI 中绑定并对数据进行增删改时可考虑 `DataSet` / `DataTable`（但现在多用 ORM 或更现代的 DTO 模式替代 DataSet）。
